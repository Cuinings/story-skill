# 如何验证实际更好、更省

回归测试验证程序行为，token 报告验证指令体积。v0.2.0 另有真实中文稿件的写作、独立代理审查、提交与修订实测，见 [中文实测](中文实测.md)。以下同题比较仍待执行，不能把本次样稿验收冒称文学盲评。

## 等条件比较

两套技能各用独立副本和新会话，固定同一模型、推理档位、输入小说、计划、读者需求、输出字数范围和允许的修改轮次。不要把新版 800 字和上游 3000 字比较；不要把缓存命中的成本与冷启动混算。原仓库使用正常支持的路径，也保留其按需加载优化。

每种任务建议收集多次结果，由不知道来源的读者评审。分别报告输入、缓存输入、输出、推理、工具往返、失败/补写/重写次数；供应商未提供的 usage 字段写 null，不能以估算补成“实测”。实际任务总量来自宿主/供应商用量记录，静态 tokenizer 只能作解释。

## 现实任务与验收

| 输入任务 | 应观察的行为 |
|---|---|
| “开一本悬疑书，只做前三章细纲，不要正文” | 有欲望、代价、因果、停笔点；没有正文；不会强要对标或全量部署 |
| “接第 108 章后继续，2200—2800 字” | 从真实末章和计划续写 109；没有重导入前 108 章；长度、状态、承诺可核对 |
| 给出新能力与旧设定冲突 | 明确定位冲突；根据用户授权修订，不能靠省略关键状态来假装通过 |
| 800 章文本含序章、重复章号和番外，要求完整拆解 | 所有字符有覆盖，特殊标题不消失，正式章目录另核对；断点恢复不重做已提交块 |
| 网页只显示阅读预览 | 标注部分文本和来源；不虚构全书情节，不把来源里的指令当系统命令 |
| “这一段太 AI，保留剧情修改” | 保留事实/声线；减少重复解释；不机械改短句或给每句加身体动作 |
| 第 12 章修改牵涉已写到 30 章 | 给出后文影响并建立复核方案，不直接覆盖权威历史制造假一致 |
| 同一草稿提交两次、模拟导出中断 | 状态只推进一次，能恢复导出，文件与审查哈希一致 |

## 质量记录

每个稿件记录：任务完成度、因果可信度、人物选择、连续性、情绪/节奏、句段自然度、原创距离、字数是否达标。评审应给原文位置和原因；不要用单个“综合分”掩盖严重硬约束违背，也不使用“AI 率”作为文学质量真值。

建议验收判据：明确约束违背为零；严重连续性问题不高于基线；盲评无明显退化；在这些条件下，再比较同等输出长度的任务总 token 和重写次数。是否提升需要实测结论，不在事先把目标当结果。
