# 百万至千万字中文长篇优化方案

本文件保留 v0.2.0 的原始诊断与设计基线；后续实现的当前用法见 [超长篇实操](超长篇实操.md)，各版本验证结果见 [改造验收](超长篇验收.md)。

2026-09-10 状态说明：以下“当前”“本轮”和未完成项均指 v0.2.0 的历史设计阶段，原始测量值继续保留。v0.4.0 已完成 311 项单测、12 项整包检查、77 次长篇 CLI 检查与 28 项断言，并验证 400/4,000 章、2,000/20,000 张卡片的合成容量；这些历史迁移、升级证据及当前 v0.5.3 入口见 [超长篇验收](超长篇验收.md)。这些结果不等于真实数百章连续创作或长程文学质量胜出。

目标是全书增长时，单章资料输入和日常维护尽量由本章涉及的人物、规则与证据决定，同时保留远期伏笔、人物知识边界、历史版本与恢复能力。本文为针对当前 v0.2.0 的设计方案；没有迁移现有书库，也没有把容量探针称为千万字创作验证。

## 1. 当前瓶颈已做容量核对

按每章2500个字符，100万约400章，1000万约4000章。新建系统TEMP隔离夹具，分别放入2000/20000张无关历史卡片，调用原版运行时，记录正文文件读取次数。夹具使用重复汉字、直接插入基础数据，不包含完整事件史、真实文学情节或模型写作。

| 操作 | 100万字符、400章 | 1000万字符、4000章 |
|---|---:|---:|
| status 正文文件读取次数 | 800 | 8000 |
| context 正文文件读取次数 | 800 | 8000 |
| prepare 正文文件读取次数 | 800 | 8000 |
| 无变化 export 正文文件读取次数 | 2000 | 20000 |
| 新增一章 commit 正文逻辑读取量 | 21,022,500字节 | 210,022,500字节 |
| 加100张较长全局硬约束后所需最小上下文 | 47,952字节 | 47,956字节 |

最后一项均超过默认16,000字节并报错，未静默截断。操作的计数包含实际执行的读取，读取量不是物理磁盘I/O或token。单机单次测得4000章时commit约18.15秒，只作为本次诊断，不能当作跨设备性能承诺。受控夹具的日常输出包仅约2.6KB，是因为只要求一张事实卡；不能由此宣称真实4000章的相关上下文也只需2.6KB。[完整探针结果](../benchmarks/results/scaling.json) · [复现脚本](../scripts/scale_probe.py)

代码原因：全书导出健康检查每文件读两遍，正常导出对未变化历史文件约读五遍；新增一章会经过两者。cards/recall在Python中读取全部卡片或章摘要，export还把所有正文内容fetchall进内存，相关操作处于数据库事务内。当前减少的是输出给模型的资料量，还没有让全部本地工作变成增量操作。

## 2. 创作资料按五层组织

| 层 | 保存什么 | 写本章时怎样使用 |
|---|---|---|
| 全书约定 | 类型承诺、叙述原则、不可突破的全局限制、终局需要保留的条件 | 只保留少量真正全局的硬约束，不能把所有设定都设为全局必读。 |
| 当前卷 | 本卷目标、关系压力、代价、进入和结束条件、跨卷未决问题 | 当前卷细化，下一卷概述，更远只留方向；按冲突结构分卷，不为凑固定字数切卷。 |
| 当前情节段 | 几个相连场景的选择、后果、资源和关系变化 | 只细化近期章节；将“预计发生”与“正文已发生”分别保存。 |
| 故事线与人物状态 | 每条线最后场景、故事时间、地点、未完动作、人物知识、物件伤势 | 多视角切回某条线时，接这条线自己的断点，而非机械接全书上一章。 |
| 证据档案 | 不可变正文版本、事实、原始伏笔、关键对话、规则与事件 | 通过实体、条件和依赖取精确原句；归档卷仍可检索，不把旧正文改写成一条含糊摘要。 |

例如甲线停在第80章审问中，乙线写到第90章；第91章回甲线，应带第80章的未完问题、在场者、谁知道什么、已亮出的证据及对应故事时间。第90章结尾只能帮助安排叙述顺序，不能代替甲线现场。

## 3. 中文连载的六种状态

**人物信息独立于作者事实。** 记录人物对某事实的已知、相信、怀疑、明确不知，附获知事件、渠道、故事时间和原文。缺记录不等于明确不知。谎言可以改变人物相信的内容，不能改变世界事实。倒叙按当时知识查询，不能拿人物未来获知的信息解释早期决定。化名、称谓及同名人物需要稳定实体ID、使用范围和获知对象。

**伏笔分清读者承诺与作者排期。** 记录首次铺垫、强化、误导解释、关联实体、触发条件、预计兑现窗口及兑现证据。第30章种下的物件在第300章重现，即使未到预计章数也要唤回。作者计划可有理由地调整；人物立下的“三日内归还”要按故事时间检查。休眠不等于已完成，归档不等于删除，不能靠虚假结案缩小上下文。

**时间分故事时间和叙述次序。** 保存场景时间区间、跨线相对顺序、赶路及恢复时间要求。未知时长只标待核，不自动判定为瞬移。跨卷跳时要明确对伤势、年龄、关系和承诺的影响。

**能力、战力和资源按适用范围记账。** 本章涉及的能力保存前置条件、代价、冷却、克制关系、规则版本；资源保存余额或范围、持有人及实际转移事件。中文“十万”“半数”“约三成”等须明确可否计算；信息不足不能假装精确。新地图可以有新规则，但旧代价不能无说明消失；例外须有授权与正文依据。不建立全世界每笔开销的账本。

**人物弧线保留不可逆后果。** 每个情节段简记欲望、选择、惯用手段、代价、关系变化和结果。比较新旧段是否只换场景重演“受辱—爆发—众人震惊”，以及人物是否真的因经历改变。相似场景也可能是有效呼应，因此只输出有原文依据的审查建议，不用相似度直接判差。

**历史修改保留影响关系。** 记录后文章节用了哪些事实、物件、获知事件、规则和伏笔。删除第20章赠钥匙，应找出后文开门和再次转交的场景，而不是重写所有后文。依赖记录未必完备，仍需要实体/原文检索与语义补审；不能宣称依赖图自动找出全部影响。

## 4. 单章上下文与中文检索

先从本章计划确定实体、故事线、故事时间和涉及规则，再拿这些对象的当前状态及直接依赖。强约束完整取回，其他候选排序后按预算选取。关键转折要补读原始铺垫；需要声线和衔接时保留相关原文段，不能全部只用摘要。

可先以如下输入预算做工程试验，之后按实稿调整。它是拟议目标，不是当前性能保证，也不包括模型推理和正文输出：

| 资料 | 建议起始预算 |
|---|---:|
| 全书约定与本次授权 | 500—1000 tokens |
| 本卷目标、当前情节段、本章计划 | 1500—2500 tokens |
| 相关人物、知识、规则及到期承诺 | 2000—4000 tokens |
| 衔接原文与本章需要的历史证据 | 2000—4500 tokens |
| 总计 | 约6000—12000 tokens |

预算不足时，先去掉不相关资料，再拆分场景核对或显式扩大本次预算；不能截掉必需事实。当前运行时预算按UTF-8字节计，不应把16000字节称作16000 tokens。摘要按输入正文版本及依赖版本缓存，依赖变化即失效；不要对上一版摘要反复再摘要，避免证据漂移。缓存是本地资料复用，不能据此承诺供应商账单一定命中缓存。

中文检索采用分工：实体ID与别名精确索引找人/物/地名；结构化字段检索适用时间、关系及伏笔状态；中文分词或字符n-gram索引找正文候选，最后回读原文核验；向量检索可作语义候选补充，不能单独决定人物身份或事实。

本机SQLite 3.50.4上，用句子“江棠把船票交给杜承安”实测：默认unicode61未匹配句内的“江棠”“杜承安”；trigram匹配了“杜承安”，未匹配两字名“江棠”。这与其连续字符分词及不足三个字符不匹配的规则一致，因此需要两字名、单字称谓和别名的专门路线。[SQLite FTS5官方文档](https://www.sqlite.org/fts5.html#tokenizers)

## 5. 运行时改造顺序

**先完成索引和数据范围。** 保留SQLite，增加实体、别名、故事线、事实版本、人物认知、伏笔生命周期和章节依赖的结构化表；对ID、范围、状态和时间建立索引。提交只读取受影响ID及其依赖，不能继续解码全书卡片。JSON保留给不规则说明与原文证据。没有依据仅因千万字就更换为更复杂服务；SQLite容量上限本身不能证明应用性能，当前探针已说明全量扫描才是直接问题。[SQLite限制说明](https://www.sqlite.org/limits.html)

**导出内容改成按需读取。** 日常从待导出队列取目标和内容版本，不先fetchall所有正文；正文按哈希去重保存，章节版本、事件和导出任务引用它。外部编辑备份仍单独保留，不能让可编辑文件直接改写内部不可变对象。状态事务只提交必要记录，导出在事务外完成，再用预期版本确认；旧队列任务不能覆盖新章版本。

**外部改稿检测不能偷偷弱化。** 仅比较mtime/size不能证明文件没变，文件通知也可能漏事件。第一阶段保留严格核验默认行为，先减少同阶段重复读取和全量内容加载。后续若增加增量校验，必须有明确的校验范围、最后完整校验版本、待核文件及通知完整性；启动、丢事件或来源不明时重新核验。未验证的历史不能报成“全书无冲突”。本机D盘为exFAT，不能设计成依赖NTFS专有日志才可运行。

**历史修订从快照建立候选分支。** 在卷末或可配置章距保存状态快照，从最近快照定位历史事实。改稿先使受影响摘要、认知和审查失效，逐项复核后才能发布新正式版本；中断时旧版可用，新分支可续接。旧delta的前像不匹配时停止，不把无错误执行等同文学一致。

建议交付分三段：P0做索引、实体范围、按需读取与明确完整性语义；P1做人物认知、伏笔状态和分线衔接；P2做历史修订分支与跨情节段的成长/重复审查。每段都需要旧schema迁移、回滚和既有书库验证，不能把当前v0.2.0直接改名为“千万字版”。

## 6. 验收分开做

容量验收：400/4000/可选10000章阶梯，独立变化卡片数量；记录候选扫描数、正文读取次数、逻辑字节量、事务时间、内存和上下文输出。日常局部操作以接近相关对象数量增长为目标，全书核验允许随全书规模增长。吞吐、总token及“节省比例”都从实际记录得到，不预填成功目标。

语义验收：至少包括跨10章回到同一故事线、跨300章回收原始伏笔、两个人物持有矛盾认知、同名与化名、倒叙、能力冷却和资源转移、旧章改动使后文失效、作者排期变化但不抹掉硬承诺。可用精选章节加结构化间隔构造长距离案例，但必须标成模拟长距，不能冒充真的写完了中间300章。

实际连续创作再逐步覆盖10章、50章、整卷的模型写作与作者反馈，保存返工原因和真实用量。千万字符合成夹具证明容量相关代码路径可以运行，不能证明千万字作品保持人物成长、叙事变化和文学质量。

本轮产物为此方案、容量探针及其实际结果。v0.2.0运行时、现有示例书库与技能包均未做架构迁移。
